# REQUEST (dev decision, no change made on any host): stop `render-env.sh` writing `RDS_DATABASE_URL`; and a question: is the rendered `.env` still needed? (ddp-sync, EC2-broker host observations, 2026-10-21)

The operator asked me to send this. **I changed nothing**: no edit to `.env`, `render-env.sh`, the systemd unit or any config.

## 1. The small request
`infrastructure/render-env.sh` (lines 109 to 112) still writes `RDS_DATABASE_URL=postgresql://user:password@host...` into `.env` on every ddp-sync start (`ddp-sync.service` runs it as `ExecStartPre`). Since OPEN-260 **every ddp-sync consumer resolves the credential live** through `rds_credentials.resolve_rds_database_url()` (scrape, archive, backfill, vote_person_backfill, the `cloud_scrape_trigger` loader call, replica freshness); the remaining mentions in `src/` are comments and docstrings. The line is therefore a snapshot that goes stale on RDS's 7-day rotation (mine stopped working on 10-21 about 03:10 UTC; the file was last rendered 10-14 15:03) and sits in a plaintext file (mode 600, owner `bitnami`) as a database password that is valid for up to 7 days after each render. **Please consider removing those lines from `render-env.sh`**, after checking that nothing in `ddp-open-states-dev`'s tooling (`os-text-extract` RDS backfill and dry-run commands, per the `rds_credentials.py` docstring) or any runbook still reads the saved variable. Keep `RDS_CREDENTIALS_SECRET_ARN`, `RDS_HOST`, `RDS_PORT`, `RDS_DBNAME`: the live lookup needs them. A hand edit of `.env` does not work (regenerated at every start; the file header says not to). My earlier report and its correction are on this branch (`b0fdd7f1`, `d9126019`).

## 2. The design question (your call; I am only reporting an observation)
`render-env.sh`'s header gives the reason the `.env` is rendered on the host: the container's network "can't reach the EC2 instance metadata service the way the bare-metal process could", and giving the container its own AWS role "is more surface than resolving them here once". **That no longer seems to be true on this host:** from inside the running `ddp-sync-ddp-sync-1` container a `boto3` STS `get_caller_identity` call succeeds as `EC2ServiceAccessReadOnlyRole` (the host's own role), and the live RDS lookups (`resolve_rds_database_url`, e.g. the USA load at 03:05 UTC today) work from inside it. So the config loader's direct path (`_load_from_secrets_manager`, "Secrets Manager, then .env file, then defaults") may be usable at startup, which would let `.env` shrink to host-specific settings. I tested one call only; I do not know when the container's access started working or whether it is the same on the votebot/ddp-api instance. Tradeoffs you will know better than I do: container start would then depend on Secrets Manager being reachable at that moment; `render-env.sh`'s re-resolve-on-every-start behaviour (the systemd comment) is useful and would need an equivalent.
